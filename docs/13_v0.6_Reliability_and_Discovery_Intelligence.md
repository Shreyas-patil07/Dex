## 1. Product direction

Dex should evolve from a watch-history and taste-based recommendation app into an entertainment identity and discovery product. The next release is not a feature race against YouTube, IMDb, MyAnimeList or Anikoto. Borrow their useful interaction and data-lifecycle contracts, not their infrastructure, datasets, branding or scale assumptions.

**Build next: Discovery Intelligence.** This means recommendation exposure and feedback instrumentation, offline ranking evaluation, and the data lifecycle required to make user-facing taste features honest and controllable.

### Non-goals for v0.6

- No streaming, playback, content hosting or redistribution.
- No watch parties or real-time social features.
- No points, ranks, Mana-like gamification or community board.
- No scraping IMDb, MyAnimeList, Anikoto or any reference site.
- No Kafka, Flink, Redis, vector database, ANN service or custom neural recommender without measured need.
- No production ranking-weight changes based on a handful of clicks.

## 2. Current baseline and release blocker

Dex currently uses React 19, TypeScript, Vite, FastAPI, Firebase Authentication, Cloud Firestore and TMDB. Taste Engine V2 rebuilds all-time and recent profiles from watch-level contribution snapshots, retrieves item-to-item TMDB recommendations from highly rated watches, uses local IDF over watched titles plus the current candidate pool, and caches candidate pools against profile_version. It serves Safe, Adjacent and Wildcard slots with controlled top-k exploration and diversity selection.

### Workstream A — Recommendation event instrumentation (P1)

**Decision:** Store first-party recommendation events in Firestore, append-oriented and separate from derived taste state. Batch events per page view. Do not add a streaming event platform.

Initial event fields:

| Field | Purpose |
|---|---|
| event_id | Client-generated idempotency key; unique per event |
| user_id | Server-derived Firebase UID; never trusted from request body |
| request_id | Recommendation response/candidate-set identifier |
| algorithm_version | Version of the ranking logic that produced the exposure |
| slot | safe, adjacent or wildcard |
| position | Zero-based/one-based position with one convention documented |
| media_type, tmdb_id | Stable TMDB title reference |
| event_type | impression, open, add_to_list, not_interested, less_like_this, more_like_this |
| event_time | Server timestamp; optionally retain client time for diagnostics only |
| surface | home_for_you or another explicitly enumerated surface |
| session_id | Opaque session correlation identifier; no auth token |

Suggested initial path: users/{uid}/recommendation_events/{event_id}. The API derives uid from the verified Firebase bearer token and enforces an allowlist for event types, surfaces, slots and payload size.

Implementation requirements:
- One bounded batch POST per rendered recommendation view; do not issue one network request per card.
- Idempotent writes keyed by event_id. Repeated delivery must not double-count.
- Record rendered exposure, not merely API response generation. If reliable viewport visibility is not implemented, label the event as rendered rather than claiming a true impression.
- Capture request_id and algorithm_version from the recommendation response.
- Never store bearer tokens, raw headers, free-form notes, or unrelated personal data.
- Add rate limits, payload limits, server timestamps, validation and tests for cross-user isolation.
- Keep raw events append-only. Derived aggregates and model features are rebuildable and versioned.
- Define retention, pause and clear controls before production collection begins.

### Workstream B — Explicit feedback controls (P1)

Add three direct controls to recommendation cards:
- More like this.
- Less like this.
- Not interested.

Do not interpret a missing click or ignored card as a negative preference. Explicit feedback must be represented as an event with idempotency and clear UI confirmation. Decide whether a title-level dismissal is permanent, reversible, or scoped to a recommendation surface before implementation.

### Workstream C — Offline recommendation evaluation (P1)

**Status: implemented in PR #22.**

The merged evaluator runs five predeclared synthetic profiles without TMDB calls or personal data. It uses the production V2 all-time/recent profile reconstruction, local IDF and candidate scorer. It reports NDCG@3, Precision@3, Recall@3, intra-list diversity and positive-feature coverage, plus a deterministic greedy MMR diagnostic.

The current five-profile baseline is recorded in [Testing and Validation](09_Testing.md). Fixture grades were authored from feature assumptions, not independently labelled by users or human reviewers. Perfect fixture NDCG/precision therefore validates a synthetic scoring path only; it is not evidence of real-user recommendation quality.

Future evaluation using later positive actions or explicit negative feedback depends on consented event data, approved retention, pause/clear controls, export/deletion hooks and sufficient observations. Do not tune the 90-day half-life, 75/25 blend, 5.5 rating baseline, +0.15 unrated signal, feature weights or MMR lambda from the synthetic fixtures alone.

### Workstream D — Data lifecycle, security and reliability (P0/P1)

See the [Data Lifecycle and Privacy Readiness](14_Data_Lifecycle_and_Privacy_Readiness.md) source inventory and release gates. Before writing behavioural data:
1. Audit Firestore Security Rules and Firebase IAM in the actual Firebase project. Admin SDK access is governed by IAM and backend authorization, not Firestore Rules. These controls are not fully represented in this repository.
2. Define user export and deletion coverage for account/profile records, watches, per-watch taste contributions, recommendation caches, legacy taste documents, future recommendation events and any later user-owned lists.
3. Define event retention, user pause/clear controls and the effect of deletion on aggregates.
4. Add Firestore concurrency, idempotency, batch-boundary and retry tests.
5. Review rate limiting. Current memory:// storage is process-local and is not a shared limit across multiple API instances.
6. Document backup and restore procedures.

Any new collection must register its owner, retention, export path, deletion hook, access policy and test coverage in the data inventory before release.

## 4. Decision register

| ID | Decision | Rejected alternative | Bias risk | Reversal / pause condition |
|---|---|---|---|---|
| D1 | Verify Render before features | Ship and debug later | Green-CI optimism | Release gate |
| D2 | Log rendered exposure before interpreting no-click | Click-only analytics | Availability bias | If viewport tracking is unreliable, label rendered exposure accurately |
| D3 | First-party Firestore events, batched per view | Kafka/Flink/third-party analytics | Mimicry of large platforms | Revisit on measured write cost or latency |
| D4 | Add explicit positive and negative feedback | Infer dislike from silence | Positivity skew | Revisit if negative feedback volume is too low to interpret |
| D5 | Offline evaluation before ranking changes | Tune by eye | Confirmation bias | If data is sparse, use predeclared fixtures |
| D6 | Dex DNA from existing vectors, with editable preferences and visible coverage | Present weak inference as fact | Flattery / false precision | Hide if backfill is incomplete or profile is sparse |
| D7 | Person pages and credits from TMDB with caching | Graph database or IMDb data | Feature envy | Pause if TMDB terms/quota do not permit it |
| D8 | User-owned typed, ordered lists, private by default | Status-only tracking forever | Scope creep | Revisit if users do not create lists |
| D9 | Search V2: query relevance first, taste rerank second; URL-persisted filters | Taste-first search | Over-personalization | Revert if query relevance declines |
| D10 | Defer episode progress; model separately from title status | Add episode fields to title watch | Planning fallacy | Revisit when real TV-tracking demand appears |
| D11 | Defer social features, watch parties and points | Build lightweight social now | Feature copying | Revisit only after privacy controls and demand are proven |
| D12 | Design export, deletion, retention and pause/clear before collecting events | Defer deletion to v1.0 | Deferral bias | Mandatory |
| D13 | TMDB remains sole catalogue; no reference-site scraping | Mirror IMDb/MAL data | Convenience | Mandatory |

## 6. Measurement principles

- Establish a baseline before setting numeric targets.
- Never judge recommendation quality by click-through alone.
- Segment exposure and outcomes by slot, position and algorithm version.
- A click is an engagement signal, not proof of satisfaction.
- A missing click is not a dislike.
- Small active-user counts make online A/B testing underpowered; prefer offline replay and predeclared fixtures.
- Track diversity, catalogue coverage, repeat exposure and explicit negative feedback alongside positive actions.

## 7. Evidence limits and bias controls

The reverse-engineering briefs are reconstructions, not source recovery. The large platforms selectively disclose architecture; their production weights and schemas are not public. IMDb was not inspected live; MyAnimeList route inventory relies partly on third-party analysis; Anikoto was text-only and its security warning came from one scanner. These sources support interaction and architecture patterns, not claims that copying them improves Dex outcomes.

The 90-day half-life, 75/25 blend, rating baseline and MMR lambda are current design parameters, not empirically tuned values. The match percentile is request-pool-relative, not a probability. Treat user profiles as summaries of logged behaviour, not ground truth about identity or taste.

## 8. Legal, privacy and catalogue guardrails

- TMDB remains the only catalogue source. Respect current attribution, caching, rate-limit and image terms.
- Do not scrape IMDb, MyAnimeList or reference sites; do not use undocumented endpoints or repurpose restricted datasets.
- Behavioural event data is personal data. Derive UID server-side, avoid tokens and free text, minimize fields, define retention, and provide pause/clear/export/deletion.
- New public profiles and lists default to private.
- This document is a technical product plan, not legal advice.
